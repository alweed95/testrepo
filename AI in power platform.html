Copilot Studio: Best Practices

Seven things that decide whether an agent is usable or merely impressive.

  1. Design topics around user intents — ask "what is the user trying to accomplish?", not "what can my system do?". Map common questions and tasks to specific topics; avoid catch-all topics that try to do everything.
  2. Each action returns structured JSON — Copilot variables pass data between steps. Structured output = predictable behaviour. Unstructured output = unpredictable agent responses.
  3. Keep actions focused — one action = one job. Small and composable beats monolithic.
  4. Use fallbacks — graceful failure beats confused silence. Offer alternatives.
  5. Test with real users early — your "obvious" UX isn't obvious to anyone else. Watch someone use it without guidance and you'll learn fast; iterate on phrasing, topic triggers and response formatting.
  6. Log conversation turns to Dataverse — track what users ask (reveals gaps in your topics) and what the agent gets wrong (reveals prompt issues). Build analytics on usage patterns.
  7. Set guardrails — what should the agent refuse to do? What data should it never expose? What should trigger escalation to a human?

The mindset shift

From "Is this correct?" → "Can I prove it was backed by data?" The goal isn't perfect AI — it's provably validated AI.

Evaluation

"Good enough to ship?"

Observability

"What broke, where?"

Explainability

"Why this output?"

The three golden rules

Everything else in this talk is an implementation detail of these. Click one to open it.

01

Separate generation from evaluation

Never let the fox guard the henhouse.

Generators optimise for fluency; evaluators for accuracy. The same model asked to grade its own work will defend it. Use a separate call, and don't hand the evaluator the generator's reasoning — it will just agree with it.

click to open
02

Do it deterministically, or gate it cheaply

If code can decide it, code should decide it.

Calculations, lookups, filtering and if/then rules belong in the flow — free, exact, identical every run. And put the free checks first: a $0 length and schema check before a $0.02 LLM judge. Most bad output never needs to reach a model at all.

click to open
03

Ask for the reasoning and the data

Chain-of-thought is your audit trail.

Make the "why" — and the source figures it leaned on — fields in the JSON; in AI Builder you simply prompt for them. That turns a rubber-stamped true into a checkable one. And it isn't only a trust device: showing the reasoning and citing the data measurably lifted our accuracy.

Architecture Evolution: Patterns 1–3

Start simple. Escalate on evidence, not anxiety. Each pattern is a rung up the ladder.

2× cost

1. Generate → Evaluate

Generate insights, one judge checks them, ship or discard.

Your baseline. If this holds, you're done.

2–5× cost

2. Iterative refinement

The judge fails it, so you retry with the reason attached.

"Claim says marathon but steps=412" → corrected to "sedentary today".

3–4× cost

3. Multi-candidate + arbiter

Generate three drafts in parallel, an arbiter picks the best-cited one.

Buys you consistency — it cuts variance, not error.

Most systems live happily on Pattern 1 or 2 — until the logs prove you need more. Then comes Pattern 4, the production shape.

Pattern 4: Task Decomposition + Layered Validation

Break the big job into small, independently-validated stages. Drop failures early.

The premise

Our first version was one big reasoning-model prompt doing everything. It was too slow for time-sensitive insights, too expensive, and not accurate enough for production — too many failure points in a single prompt. So we broke the job apart: deterministic calculations out of the LLM, less context per step, and simpler (standard/basic) models per stage — which increased accuracy.

The 10 stages (PHI)

02Claim generationstandard

05Per-suggestion validation — Judge L2basic
06Reassemblyno LLM

The generator never writes suggestions. It only says what is true and which metrics prove it. Narrowing the job to three fields is what lets a standard model do it — no reasoning tier required.

Step 2 — Claim validation (Judge L1)

A second standard-tier call re-derives the protocol from the same dataset and rules on each claim independently. It must show its working — rank 1, rank 2, the band and the count — so a rubber-stamped true is visible as one.

Once L1 passes, the traceability line becomes a trusted subset. Every metric=value pair in it has been confirmed against the source. That is what makes it safe to send downstream instead of the dataset — and why everything after this point fits on a mini model.

Step 3 — Suggestion generation loop

One mini-model call per claim, fed only that claim's traceability line. Click a claim to isolate its iteration.

traceability → generator input generator → suggestions

Step 4 — Suggestion validation

A second loop, nested inside the first. The box of four suggestions splits apart and every one of them gets its own mini-model call, on its own, with nothing but that claim's traceability line for company. Three claims × four suggestions = 12 independent judgements, each returning a bare true or false with its reason.

traceability → model input generated suggestion verdict
No box here can see any other box. Each judge is handed one sentence and the subset that is supposed to justify it — which is what keeps the payload near 240 tokens and the tier on mini, and is also the blind spot the quality gate exists to cover.
The six survivors go straight to the email on the right. Reassembly is an array filter, not a prompt — nothing is re-generated, so nothing can drift between validation and send.

Step 5 — Quality gate

Every prior call judged one thing in isolation. This is the only call that sees the assembled set — so it is the only one that can catch a problem that exists only between insights. Standard tier, one call, and the payload is the finished insights, not the dataset.

Isolation is what made the mini models viable, and this is the price of it. A judge that only ever sees one suggestion cannot know that two claims booked the same evening. The gate buys that back for one standard-tier call on ~1,300 tokens.

Best Practices & Takeaways

Now you've seen it built — here's how to keep it reliable.

  1. Always JSON contracts — never trust free text; parse + schema-validate every output.
  2. Validate, don't trust — check length, schema, types, and that cited values exist in the source.
  3. Separate generation from evaluation — never let a generator grade its own work, and keep validators independent (don't feed them the generator's reasoning).
  4. Keep deterministic work out of the LLM — calculations, lookups and filtering belong in the flow: free, exact, and identical every run.
  5. Ask for the reasoning and the data — having the model output its chain-of-thought and cite the source figures it used measurably lifted our accuracy, as well as making the answer auditable.
  6. Right-size the model — start with the cheapest tier that works; decompose the task so basic/standard models can do the job instead of premium.
  7. Fail fast, and gate every step — bad output early? Stop. Each validator is also a gate: below threshold → halt and retry, don't ship it.
  8. Externalise prompts where it helps — SharePoint/Dataverse, versioned; easier to edit and A/B test than prompts buried in a flow.
  9. Build retry mechanisms with feedback — on failure, tell the model exactly what it got wrong; cap at 2–3.
  10. Use only the data you need — don't dump the whole dataset into the model. Send the relevant slice to cut cost and lift accuracy — though sometimes the full set is right. Find the balance.
  11. Start simple, evolve on evidence — don't over-engineer; add complexity only when your logs prove you need it.
  12. Log what matters — to Dataverse — durable, queryable run history; you can't improve what you can't measure.
